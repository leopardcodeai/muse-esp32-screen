The version is `esphome: project: version` in `firmware/muse-esp32-s3-box-3-screen.yaml`; the box reports it in `muse_get_state` and on its info screen. Dates are the day the firmware ran on the box. Wrong turns are recorded, because the same mistake comes back otherwise.

## Muse Web Screen 1.8.23, 19 November 2026 (web, no add-on rebuild): fast figure, start pose, no blue icon

- **The figure loads about 14 times lighter.** The owner (19.11.2026): "schnell laden und eine schnelle start pose". Each pose was an animated PNG of 72 frames at 320 px, 5 to 6 MB (about 28 MB for the light set, 53 MB with the dark copies), and Muse took about 4 s to appear on the Samsung Tab on a cold start. Each pose is now also one lossy WebP sheet, all frames in a grid with the layout in the file's XMP chunk (`muse-sheet="frames=72 columns=9 size=320 delay=41.667"`): idle 5540 KiB to 325 KiB, the light set 27.6 MB to 1.9 MB, both sets 52.7 MB to 4.0 MB, 40 dB PSNR, no difference to see at 480 px. New module `figure_sheet.js` (sniffs PNG or WebP, cuts the sheet with `createImageBitmap`, which Safari has too; an animated WebP would need WebCodecs, which Safari lacks). Every pose tries `muse_<name>.webp` first and `muse_<name>.png` second, so a folder from before keeps working; idle's head start now holds until its PNG is in, not just until the WebP answered 404.
- **Start pose.** `muse_start.webp` (and `dark/muse_start.webp`): idle's first frame as one still, 8 KB, asked for together with idle at high priority. It stands in for idle and every pose that borrows idle until idle's own frames are decoded, so the first frame shows Muse at once; then the animated idle replaces it. New log lines `figure start pose ready after N ms` and `figure idle animated after N ms (72 frames)`. A folder without a start pose waits for idle as before; no blue, no placeholder in between.
- **New tool** `tools/make_figure_sheets.py --src <folder>` writes the sheets and the start pose for a folder and its `dark/` (also for another figure style); `tools/make_muse_web.py` calls it after the PNGs (`--sheets` for only that step). The service worker caches the sheets and both start poses at install (`PRIVATE`) and serves `.webp` figure files from the cache like the PNGs; `muse_*.webp` is ignored by git and Vercel like `muse_*.png`.
- **No blue figure in the app icons.** `web/icons/` (192, 512, maskable 512, Apple 180) show a neutral grey silhouette (the stand-in of `figure.js`: round body, darker lower half, two eyes) on a near-black squircle, drawn by the new `tools/make_web_icons.py`. With `--own <picture>` the same tool cuts the owner's own app icon into `web/local/icons/` (private); the homeassistant repository's deploy script puts those in place of the public icons on the add-on, so the installed app there shows his Muse face while the repository stays neutral.
- Tests: 318 (new `test/figure_sheet.test.js`; the older loading-order tests now name their PNG-only folder explicitly).

## 4.3.2, 18 November 2026 (built, not yet flashed)

- Memory: code and read-only data now run from PSRAM (`execute_from_psram`, which sets `CONFIG_SPIRAM_FETCH_INSTRUCTIONS` and `CONFIG_SPIRAM_RODATA`). lwIP's, Wi-Fi's and Bluetooth's BSS moved to PSRAM (`CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY`), Wi-Fi keeps its hot paths in flash (`CONFIG_ESP_WIFI_IRAM_OPT` and `CONFIG_ESP_WIFI_RX_IRAM_OPT` off), and the media player's voice pipeline uses 8 instead of 16 static TX buffers. Bluedroid's heap for the BLE proxy also lives in PSRAM (`esp32_ble: use_psram`). Together this makes room for the display's DMA transfers, the microphones and TLS; the box's internal RAM was the tightest resource.
- TLS uses software AES (`CONFIG_MBEDTLS_HARDWARE_AES` off). At 240 MHz the hardware engine is no faster, but it bounces PSRAM records through DMA-capable internal RAM, the memory the display needs during a handshake. Software AES keeps the handshake out of that path.
- Build: the home overlay (`firmware/muse-esp32boxs3-screen.home.yaml`) compiles. Static DIRAM is 38.2% used (130,499 of 341,760 bytes, 211 KB free); flash is 95.4% used, 5% of the app partition free. The public base compiles too, at 36.2% static RAM. The app partition was already tight before this change; the limit is the overlay's TV package and figure, not the memory options.
- Not flashed: the box's fixed home address did not answer ping or port 6053, Home Assistant showed the box's entities as `unavailable`, and no mDNS record appeared. The firmware keeps ES7210, ES8311, I2S, `voice_assistant` and `micro_wake_word` (okay_nabu, hey_mycroft, muse_hey_jarvis, alexa), but audio and wake word are unverified at runtime until the box is on.
- To flash when the box is on: `esphome run firmware/muse-esp32boxs3-screen.home.yaml --device muse-esp32boxs3-screen.local`, then read `esphome logs`, call `python3 tools/muse_screen.py hw` and test a wake word and a voice question.

## 4.1.0, 7 October 2026

- Route maps are stitched from the 256 px tiles of a `{z}/{x}/{y}` server (substitution `map_tiles`, OpenStreetMap's own by default) over one kept TLS connection, with the attribution the tiles require on the card. Measured: 4 tiles in 1.7 to 2.1 s. Until 4.0 the map came as one picture from Wikimedia's map service, whose terms allow that for Wikimedia projects only.
